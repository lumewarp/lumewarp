# Lumewarp

LLM gateway meant to beat LiteLLM on performance and manageability. Full design: `docs/architecture.md` (read it before any non-trivial change).

## Layout (monorepo)

- `gateway/` — data plane, Rust (tokio, hyper, rustls, arc-swap). Cargo workspace. `gateway/plugins/` holds the example WASM plugins (`router/`, `auth/`, `a2a-middleware/`) and `build.sh`.
- `control-plane/` — Python 3.12+, FastAPI, SQLAlchemy + Alembic (one squashed baseline migration; Lumewarp has never been deployed, so keep no upgrade path), Authlib, grpcio. Managed with uv.
- `ui/` — Admin UI, React + Vite static SPA (TanStack Query/Router), components are shadcn/ui on Radix. Built output is served by the control plane; no Node at runtime. `pnpm check` runs the type check and `scripts/check-shadcn.mjs` (no legacy classes, no native elements or Radix imports outside `components/ui/`, no `@layer components`; no allowlist), and CI runs Playwright.
  - Help text: static help goes in a `hint` prop, which every field, `Section`, `EditPage` and `PageHeader` renders as a "?" tooltip, never inline. Keep only help that changes what is entered or warns about a non-obvious consequence (a bound, what empty means, a secret shown once), in one sentence and without examples ("e.g.", "such as"). Drop text that restates the label or describes the page. Live text derived from state (a formatted value, a loading or fetch error, what an empty value resolves to) is a field's `note` and stays visible; errors, empty states and confirmations stay inline. A toggle that turns a settings group on or off is a switch: on an EditPage it is the `Section`'s `toggle` (at the right of the header, with buttons such as Test now in `actions` beside it), elsewhere a `SwitchField`; the group's fields show only while it is on. `CheckField` is for one-off choices.
- `proto/` — protobuf schema for the config snapshot and the config-stream gRPC service. Single source of truth for types on both sides.
- `bench/` — mock upstream (fixed latency, SSE streaming) and load scripts comparing Lumewarp vs LiteLLM.
- `deploy/` — Helm chart, Docker Compose deployment (`deploy/docker/`, documented in `docs/operations/docker.md`), Prometheus rules, Grafana dashboards.
- `docs/` — the manual (VitePress, English, organised by reader; `pnpm dev` / `pnpm build`), the single source for running, configuring and administering Lumewarp; the READMEs are only a quick start and links. Describes the current state only. `architecture.md` (Traditional Chinese) is the design. `pnpm build` generates both OpenAPI documents and fails on a dead internal link (CI `docs` job); `docs-pages.yml` publishes main to <https://lumewarp.github.io/lumewarp/>. Admin UI screenshots come from `docs/scripts/screenshots.sh` (`ui/e2e/docs-shots.spec.ts`, `serve.py` docs mode); rerun it when a photographed page changes.
- `.claude/skills/` — `lumewarp-plugin-dev` (templates for all five plugin kinds, SDK and control plane by git tag; `scripts/check-plugin-templates.sh` builds them against the tree in CI) and `port-router-to-rust`.

## Non-negotiable rules

1. **Hot path stays fast.** The gateway request path never touches a database, never calls the control plane, and never runs Python. It reads only the in-memory config snapshot. Counters and usage events are emitted asynchronously.
2. **Python only in the control plane.** Customization of auth providers is a Python plugin registered via entry points (`lumewarp.auth`, `lumewarp.authz`). Python plugins produce declarative output compiled into the snapshot. Gateway-side plugins (router strategies, upstream auth, A2A middleware) are WASM components loaded from three directories at startup (`docs/plugins.md`, `docs/router-strategies.md`), declaring their settings as schemas the control plane and UI read; built-in strategies and built-in auth stay native. Per-request hooks exist only as an opt-in external gRPC call with a timeout and a default route.
3. **Providers: OpenAI-compatible only.** Upstreams are vLLM and OpenAI (plus any OpenAI-compatible endpoint). Do not add translation layers for other providers. Pass through unknown request fields (e.g. vLLM `extra_body`, guided decoding) untouched.
4. **Config is an immutable versioned snapshot** pushed over a gRPC stream (full, then deltas; ACK/NACK). Gateway swaps atomically and persists the last good snapshot to disk so it can boot without the control plane. Gateway also supports a standalone YAML mode with the same schema.
5. **Observability is a feature, not an afterthought.** Every new gateway path gets Prometheus metrics (`lumewarp_*`, see the table in `docs/architecture.md`) and OTel spans. No API-key-level labels on metrics. Never log prompts/responses by default.
6. **Performance claims need numbers.** Any change on the gateway request path must run the `bench/` suite; don't regress p99 overhead.

## Current state

The Rust gateway with its bench against LiteLLM, the control plane, the gRPC config stream, usage and budgets, the Admin UI, identity, routing, the model catalog, self-service keys, credential storage, the Playground (own keys only, through the gateway with a short-lived `lwpg.` token), MCP/A2A proxying and WASM gateway plugins are implemented. `docs/architecture.md` lists what exists and what is deferred.

Identity, routing and observability:

- Tenancy: org → teams → members (admin/member) and service accounts → API keys. Orgs and org admins exist (`orgs`, `org_admins`, `teams.org_id`) and org administration is inherited by their teams in the control plane only (`RequestAuthz` for permissions, `keys.owners` for key ownership); the authz backend answers direct relations and `member` stays direct membership. Installation admins and org admins appear in the lower admin and member lists with `inherited_from`/`direct` (read-only there, no rows written) and may own keys in every team they administer under the team's member defaults; removing a membership or admin role suspends (`owner_removed`) only keys in teams where nothing else still allows the owner. The org API exists: installation admins create, rename/set policy, archive and assign org admins; an org admin reads its own orgs and their per-team usage, creates and archives teams in them, and reads their audit (org-level events included). `POST /teams` takes an explicit `org_id`; there is no default org. `DELETE /teams/{id}` archives: one transaction revokes every key (rotation-grace hash included), deactivates the team's service accounts, frees the name (unique only among live teams) and the compiler skips the team; org archiving needs no live team and blocks new ones. Service accounts also have a deactivated state the compiler respects. Installation admins are rows in `installation_admins` (`proxy_admin` unique, or `admin`); the first verified login matching `LUMEWARP_INITIAL_ADMIN_EMAIL` becomes `proxy_admin` while none exists, a break-glass password opens an emergency session, and a break-glass session or the proxy_admin can transfer the role. The `proxy_admin` is the highest role and its account is protected from other installation admins.
- Admin login via OIDC (cookie sessions + CSRF); the IdP authenticates only and no claim grants a role. Authorization is pluggable (`builtin`, `openfga`, `http`, or a `lumewarp.authz` entry point) behind `check(user_id, relation, resource)`, where a resource is an org or a team and every backend (built-ins included) loads through the `lumewarp.authz` entry point; installation roles are read from Postgres and never asked of the backend, and backend errors are never denies. A key reconciler suspends keys of members removed in an external IAM.
- Gateway routing: retries (before any response byte, budgeted), fallbacks, circuit breaker, active health checks, LOWEST_LATENCY, VLLM_LOAD, traffic split with sticky hashing — each gated by a snapshot capability the control plane emits only when used.
- Observability: Prometheus alert rules (promtool-tested), Grafana dashboards, control-plane `/metrics` on its own listener.
- Gateways and shared limits (`docs/architecture.md`, "跨 gateway 共享限流與多個 gateway"): every process is one gateway, with an id generated at startup (`<hostname>-<8 hex>`, `Hello.gateway_id`); a restart is a new gateway, and its disconnected row is deleted after 24 h. A token is a scope credential with a label, not bound to an id; any number of gateways may share it. Sessions, usage attribution (`ReportRequest.gateway_id`) and plugin support are per gateway; an `INVALID_CONFIG` NACK quarantines a version for the whole scope, while `UNSUPPORTED_FEATURE` skips it only for the gateway that lacks the plugin or capability. rpm/tpm are sliding windows on wall-clock minutes, max_parallel an in-flight gauge; with `LUMEWARP_SHARED_LIMITS_REDIS_URL` a background task (never the request path) `HSET`s absolute per-minute counts to Redis under each gateway id and reads the other gateways' counts, with a fair share between syncs; Redis down falls back to per-gateway counting (N x). Helm can ship Valkey (`redis.enabled`).

The model catalog (`docs/architecture.md`, "模型目錄已實作"):

- Names: a client calls a model, an alias or a router, one namespace, all renameable, referenced by id. The response `model` is the called name, without buffering.
- Grants by id, checked against the called name. Rollback restores the catalog by id.
- Usage records the served model plus alias, router, fallback and attempts. No access log: a request is looked up in OTel by `x-lumewarp-request-id`.
- Strategies are WASM plugins loaded from `LUMEWARP_ROUTER_PLUGIN_DIR`, reported in `Hello.plugins` with their schemas, validated on write; the four built-ins (`weighted`, `least_in_flight`, `lowest_latency`, `vllm_load`) are native.
- Model types: every model has one required `model_type` (`llm`: `/v1/chat/completions`, `/v1/completions`, `/v1/responses` POST only with ids passed through; `embedding`: `/v1/embeddings`; `transcription`: `/v1/audio/transcriptions|translations`, multipart parsed strictly by the gateway; `decision`: `/v1/decisions`, `/v1/systemone`). Aliases and routers take their target's/members' type, a router's members, splits and fallbacks share one, and a call on another type's endpoint is 400 `model_type_mismatch`. Probes and Test now are typed (transcription sends a generated silent WAV); usage records `audio_ms` and transcription can be priced per audio second; usage groups by `endpoint` and `model_type`; the Playground lists `llm` only. There is no OCR type.

MCP, A2A and gateway plugins (`docs/architecture.md`, "MCP gateway", "A2A gateway", "Gateway plugin（WASM）"; `docs/plugins.md`):

- MCP: `POST /mcp` is the key's aggregate server (names `<server>__<name>`, split at the first `__`), `POST /mcp/servers/<name>` a single upstream; MCP 2025-11-25 with 2025-06-18 pass-through. Sessions are sealed with `LUMEWARP_GATEWAY_ID_KEY` (stateless across replicas), upstream request ids become `lw:<server>:<id>`. Grants reach a server and its tools (a granted server exposes all its prompts); `tools/call` counts against the key's RPM. `review_mode` is `tofu` (default) / `manual` / `off`; withheld and TOFU first-sight definitions are reported in `CatalogReport`, and the control plane's first report for a name wins.
- A2A: `/a2a/<agent>` (JSON-RPC + SSE), `/a2a/<agent>/.well-known/agent-card.json`, `/a2a` list; `A2A-Version: 1.0` required, push notification config refused. Task/context ids are `lwt.` tokens owned by the key; `ListTasks` is forwarded only for `passthrough` agents. Cards are rewritten from `LUMEWARP_GATEWAY_PUBLIC_URL` (one JSON-RPC interface, `X-Lumewarp-Key` scheme, no signatures, push off); one `a2a-middleware` component per agent.
- MCP and A2A accept exactly one `X-Lumewarp-Key` (no bearer, no `lwpg.`), refuse revoked/suspended/expired keys, and accept `BUDGET_EXCEEDED`; they emit usage events and metrics but have no budgets or limits of their own (A2A is not rate limited).
- Gateway plugins are WASM components in `LUMEWARP_ROUTER_PLUGIN_DIR`, `LUMEWARP_AUTH_PLUGIN_DIR` and `LUMEWARP_A2A_MIDDLEWARE_DIR`, read once at startup (a replaced file needs a restart); built-in strategies and built-in auth are native. A call is bounded by `Router.plugin_timeout_ms` or `PluginRef.timeout_ms` (0 = 60 s), 32 MiB per instance and `LUMEWARP_PLUGIN_MEMORY_LIMIT_BYTES` in total. `Hello.plugins`/`plugin_abi` report them; `/plugins` lists them.

Self-service keys and credentials (`docs/architecture.md`, "Admin UI", "憑證儲存與稽核"):

- Self-service keys: any IdP user signs in just in time with no grants and manages their own keys in the teams they belong to or administer by inheritance; a team sets `max_keys_per_member` and `max_member_key_lifetime_seconds`, and `GET /users/me` returns effective models, limits, key limits and the month's remaining budget. A member resumes their own `owner` and `owner_removed` suspensions; `admin` and `owner_deactivated` need an administrator.
- Rotation grace: `grace_seconds` defaults to 0 and is at most 24 hours, with one previous hash; both secrets authenticate as the same key and usage stays on it, and the gateway stops accepting the old one at its own expiry from the snapshot alone. Key create, rotate and limits-only update are limited to 30 attempts per 60 s per principal and operation, per process, and a 429 is not audited.
- Admin UI: `/my-keys` is a plain member's home, a team's Keys tab manages its keys, access states are not denials, and one dialog above the router shows every one-time secret.
- Credentials at rest: only sha256 hashes and environment references, the OIDC nonce/PKCE in an AES-GCM cookie, `api_key_ref`, `metrics_url` without a query, and an allowlist for audit details.

API documents: the control plane's comes from FastAPI and `tests/api/test_openapi.py` requires a description on every operation and request field (`api/field_docs.py`), security on every non-public operation and typed 2xx responses; the gateway's is built by `lumewarp openapi` from the `ENDPOINTS` and `error::CODES` tables, so a new endpoint or error code goes into those tables. A behaviour change updates the manual page that describes it in the same commit.

Acceptance suites: `scripts/e2e-core.sh`, `scripts/e2e-mcp.sh`, `scripts/e2e-a2a.sh`, `scripts/e2e-identity.sh` (needs `scripts/dev-idp.sh up`), `scripts/load-e2e.sh`, `ui/` Playwright (`pnpm test:e2e`), and `bench/` A6 for request-path changes. The e2e suite scans the database for plaintext credentials.

Deferred: MCP resources/subscriptions and streamed `GET /mcp`, human approval of tools, the stdio sidecar, MCP OAuth resource server and upstream token custody; A2A push notifications, gRPC/REST binding, card signing and `ListTasks` for non-`passthrough` agents; plugin hot reload and signing; MCP/A2A rate limits and budgets.
